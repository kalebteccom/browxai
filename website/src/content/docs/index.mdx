    <div class="browx-lede">
      browxai is an open source MCP server that lets an AI agent drive a web
      page or a native app with the same small set of tools.
    </div>
    <div class="browx-about">
      An agent gets a compact, readable view of the page and a short list of
      tools to find, click, fill and read it. browxai drives eight engines in
      three families: five browsers (Chromium, Firefox, WebKit, real Safari
      and real Chrome on an Android phone), two native-app engines on an
      Android emulator and the iOS Simulator, and a desktop Electron app. By
      default it launches the installed Google Chrome on one default profile
      per workspace. Every capability past the default four (read, navigation,
      action and human) starts off until you switch it on. It works with any MCP client over
      stdio, and ships a typed TypeScript SDK.
    </div>

<div class="browx-section not-content">
  <h2 class="browx-section-title">What you get</h2>
  <div class="browx-section-sub">
    browxai owns its transport to all eight engines it drives, and the session
    lifecycle with it. When a task moves to a native app, a desktop app or your
    host machine, browxai follows it under a capability you switch on.
  </div>

  <div class="browx-grid">
    <div class="browx-card">
      <span class="browx-card-mark">Surface</span>
      <h3>Token-efficient</h3>
      <div class="browx-card-text">
        <code>snapshot()</code> is a scoped, paginated, budgeted accessibility
        tree. <code>find()</code> returns ranked candidates with evidence.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Native</span>
      <h3>Native apps, same tools</h3>
      <div class="browx-card-text">
        Switch on <code>native-device</code> and <code>find</code>,
        <code>click</code> and <code>fill</code> drive an app on an Android
        emulator or the iOS Simulator. The tree comes off the app's view
        hierarchy, with the same refs a page gets. Android is verified against a
        live emulator; the iOS lane is newer and needs a WebDriverAgent you run.
        Native apps run on an emulator or simulator only, with no
        real-device lane.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Desktop</span>
      <h3>The Electron app you have open</h3>
      <div class="browx-card-text">
        An Electron app is Chromium, so one started with
        <code>--remote-debugging-port</code> answers the same CDP browxai
        already speaks. Attach to an app such as VS Code and
        <code>snapshot</code> and <code>find</code> read its UI. It needs
        <code>byob-attach</code>. The engine is attach-only, <code>navigate</code>
        refuses, and whether a port opens at all depends on the app and its
        version.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Host</span>
      <h3>Reaches past the tab</h3>
      <div class="browx-card-text">
        Switch a capability on and browxai writes the real OS clipboard, or pulls a login and a TOTP code from 1Password,
        Bitwarden, LastPass or <code>oathtool</code>. File IO is rooted at one
        workspace directory. All three capabilities start off.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Safety</span>
      <h3>Default capabilities</h3>
      <div class="browx-card-text">
        Capability-gated tools, an origin allow and block list, confirmation
        hooks, and a hard anti-wedge deadline on every call. Arbitrary JS, full
        response bodies, the OS clipboard, your password manager, the native
        engines and attaching to a desktop app are all off until you opt in.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Clients</span>
      <h3>Model-agnostic</h3>
      <div class="browx-card-text">
        Any MCP client over stdio: Claude, Codex, or anything else that speaks
        the protocol. A typed TypeScript SDK runs the same tools from a script.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Sessions</span>
      <h3>Sessions and lifecycle</h3>
      <div class="browx-card-text">
        Chromium sessions launch the installed Google Chrome, or the bundled
        Chromium when Chrome is missing, on one default profile per workspace.
        Sessions are isolated contexts: persistent, incognito, or attached to a
        Chrome you already have open, on your desktop or on a plugged-in Android
        phone. Headed and headless. Pick the engine per session, so one server
        can hold a Chromium page and an emulator app at once.
      </div>
    </div>
    <div class="browx-card">
      <span class="browx-card-mark">Access</span>
      <h3>Sites behind bot protection</h3>
      <div class="browx-card-text">
        By default browxai does not defeat or spoof bot detection, and it cannot
        guarantee access to any site. When a challenge needs a person,
        <code>browxai chrome login</code> opens the installed Chrome on the
        workspace profile with nothing attached. Clear it by hand, quit Chrome,
        and later sessions on that profile reuse the cookies. The off-by-default
        <code>stealth</code> and <code>captcha</code> capabilities patch four
        browser properties and hand captchas to a third-party solving service.
        Read
        <a href="/guides/sites-behind-bot-protection/">Sites behind bot protection</a>.
      </div>
    </div>
  </div>
